# 0002. Better Auth over Auth.js

> Last updated 2026-10-30 · reflects commit [`a894636`](https://github.com/m-danie/job-tracker/commit/a894636)

- **Status:** Accepted
- **Date:** 2026-10-18

## Context

Sign-in needs email + password and GitHub OAuth, with sessions stored in our own
Postgres database. A demo mode and rate limiting were likely to follow.

## Options considered

- **Auth.js**: very good for OAuth, but its Credentials (email + password) provider is
  deliberately limited and leaves password storage and sessions to you.
- **Better Auth**: email + password, OAuth, database sessions, rate limiting and a plugin
  system (anonymous users, 2FA, organizations), plus a Drizzle adapter.
- **Hosted (Clerk, Auth0)**: least work, but user data lives with a third party, and the
  free tiers and lock-in matter for a long-lived project.
- **Writing it myself**: not worth the security risk.

## Decision

Better Auth with the Drizzle adapter. Its tables are generated by its CLI into
`src/db/schema/auth.ts` (`pnpm auth:generate`) and are never edited by hand.

## Consequences

- One user can have several sign-in methods (`account` rows). Account linking is on for
  GitHub, which only shares verified emails, so the same email means the same person.
- Demo accounts came almost for free with the `anonymous` plugin
  ([0006](0006-demo-accounts-with-anonymous-users.md)).
- Better Auth only checks password length, so the other password rules are enforced in a
  `hooks.before` middleware in `src/utils/auth.ts`.
- `nextCookies()` must stay the last plugin, or server actions can't set the session
  cookie.
